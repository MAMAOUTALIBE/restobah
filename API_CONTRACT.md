# STC internal integration contract

All paths end with `/`. Frontend accesses `/api` through the Vite proxy; production uses same-origin reverse proxy. Errors: JSON `{detail: string, errors?: object}` with appropriate 4xx/5xx. `detail` is always displayable French text: the business refusal itself (e.g. `Cette adresse est en dehors de notre zone de livraison.`) or the first field error prefixed with its French label (e.g. `Mot de passe : Ce mot de passe est trop courant.`); `errors` keeps the raw DRF structure. Credentials include cookies; write requests require `X-CSRFToken` obtained via `GET /api/auth/csrf/` (sets csrftoken cookie and a persisted session cookie; guest orders without a valid initialized session receive 409 and must bootstrap again). No frontend price is trusted.

## Catalog
`GET /api/products/` returns Product[]: existing id, name, category (French string), description, summary, price (JSON number, current server price), regularPrice (price before discount), discountPercent (integer, 0 if none), image (existing local asset key OR uploaded absolute/relative URL), badge, rating (string, empty = hidden; must come from verified reviews), vegetarian, available (false when the product, its promotion window or its source is unavailable, or when a required option group has fewer available choices than its minimum), allergens:string[] (always a list), optionGroups: [{id:string,name:string,min:number,max:number,choices:[{id:string,name:string,price:number}]}]. `options` may remain a boolean for compatibility. Choices are ids in order payloads. Product 90 is the real server-side 30%-off promotion of product 2: price 11.13, included as a separate product flagged promotional:true so it can be excluded from regular grid and opened through banner.
`GET /api/categories/` returns `[{name,position}]` in administration order; the frontend lists only categories having at least one regular product.
`GET /api/restaurant/` returns `{name,address,city,hours,days,deliveryFee:number,minDeliveryTotal:number,deliveryPostalCodes:string[],orderingEnabled:boolean,isOpen:boolean,demoMode:boolean,paymentMode:'simulation'|'stripe'|'on_site',openingHours?:...,pickupEnabled,deliveryEnabled,pickupDelay:string,deliveryDelay:string,contactPhone?:string,contactEmail?:string,legalNoticeUrl?:string,privacyUrl?:string,termsUrl?:string}`. The five optional contact/document fields are explicitly whitelisted and validated; empty or invalid configuration produces empty strings. Document URLs must be public HTTPS URLs without credentials; client approval flags and other settings/secrets are never exposed. `deliveryEnabled` is false when no postal code is configured; such delivery orders are refused. Demo defaults ordering open regardless wall clock; production observes hours and closures. `days`/`hours`: `Tous les jours` + periods when every day shares the same hours (e.g. `11h30 – 14h30 · 18h30 – 23h00`), otherwise today's periods (`Aujourd’hui (lundi)`, `Fermé` or `Fermé exceptionnellement`). A service continuing after midnight also appears in this summary until its closing time. `GET /api/health/`.

## Orders
POST `/api/orders/` with header `Idempotency-Key: uuid`:
`{mode:'À emporter'|'Livraison',items:[{productId:number,quantity:number,choices:string[]}],customer:{name,email,phone,address?,postal?,city?,note?},paymentMethod:'simulation'|'stripe'|'on_site'}`. Response 201 or 200 replay: `Order`.
Order: `{id:string,date:string,total:number,subtotal:number,deliveryFee:number,mode:string,items:string[],status:'confirmed'|'preparing'|'ready'|'completed'|'cancelled'|'pending_payment',paymentMethod:'simulation'|'stripe'|'on_site',paymentStatus:'simulated'|'pending'|'due'|'paid'|'failed'|'cancelled'|'refunded',accessToken?:string,demoMode:boolean,lines:[{name,quantity,unitPrice,total,choices:string[]}],history:[{status,date}],customer?:{name,email,phone,address,postal,city,note}}`. `paymentMethod` is fixed by the server at creation and persisted as the immutable payment origin; changing the restaurant configuration does not reclassify an older order. On-site collection/refund ledger entries and staff identities are not exposed by the public API. Return accessToken only at creation/replay to authorized creator; GET token authorized may omit it. Anonymous guest client saves id+accessToken only (avoid storing customer PII). Never return any order without owner session/staff or matching secret token. Idempotency scoped to session or user, changed payload same key returns 409.
GET `/api/orders/` returns authenticated user orders (the frontend also shows the guest orders referenced on the device). GET `/api/orders/{id}/?token=...` returns authorized Order. POST `/api/orders/{id}/payment/` accepts `{token?:string}` returns `{url:string}` Stripe-hosted checkout (test keys only), server amount, session lifetime 31–41 min (`expires_at`), idempotency key `stc-checkout-{id}-{10-min window}`; 409 when the session expired or when the unpaid order is older than `STC_PENDING_PAYMENT_MINUTES` (the order is then cancelled). `POST /api/payments/webhook/` signature checked (Stripe HMAC, 5-min tolerance), test mode only, idempotent events. For simulation order is persisted confirmed/simulated and confirmation e-mails are sent after commit. For stripe order pending_payment until verified webhook (which sends the e-mails). A payment completed on an order cancelled meanwhile is recorded as `cancelled`/`paid` (refund required, logged) and becomes `refunded` with the `charge.refunded` webhook.
Confirmation e-mail: customer (lines, total, tracking link `FRONTEND_URL/?order_id={id}&token={accessToken}`) and, when `STC_ORDER_NOTIFICATION_EMAIL` is set, the team (contact details, note, admin link). The frontend imports such a link as a guest reference and removes the token from the address bar.
For `on_site`, creation returns `confirmed`/`due` and schedules one confirmation after commit. The client explicitly commits to pay the displayed total at pickup or delivery; no Stripe session is created. Preparing/ready is permitted while due; completion requires collection recorded as `paid`. Only active staff with `view_order`, `change_order` and `record_onsite_payment` can POST the CSRF-protected CRM collection/refund actions. Amount, actor and timestamp come from the server, with locked rows, an immutable event ledger and idempotent repeats. Cancellation before collection marks payment cancelled; a full physical refund is declared by an authorized operator after collection. Partial refunds are outside this delivery. The existing public demonstration retains its configured simulation mode until the client prerequisites are supplied and verified.
Throttling: `orders` scope applies to order creation (POST) only; history polling uses the general anon/user rates (`ANON_THROTTLE_RATE`, `USER_THROTTLE_RATE`, default 3000/hour).

## Accounts
GET `/api/auth/me/` -> `{user:null|{id:number,name:string,email:string}}`.
POST `/api/auth/register/` `{name,email,password}` -> `{user}` signed in.
POST `/api/auth/login/` `{email,password}` -> `{user}`.
POST `/api/auth/logout/` -> `{detail}`.
POST `/api/auth/password-reset/` `{email}` -> generic `{detail}`. Dev email to private file (not API output); production configured SMTP. Reset frontend link `/?reset_uid=...&reset_token=...`.
POST `/api/auth/password-reset-confirm/` `{uid,token,password}` -> `{detail}`.
POST `/api/auth/delete-account/` `{password}` -> `{detail}` authenticated, `auth` throttle; deletes account, addresses and favourites, logs out; orders are kept and detached; staff accounts refused (400).
GET/POST `/api/addresses/`; PATCH/DELETE `/api/addresses/{id}/`. Address `{id:number,label,name,phone,address,postal,city}` owner scoped.
GET `/api/favorites/` -> number[]; PUT `/api/favorites/` `{productIds:number[]}` -> number[] authenticated.
Django admin `/admin/`: catalog/options, restaurant/hours/closures, orders/transitions/history, payments, customer addresses, promotions.

## Division of ownership
Backend agent owns backend/ exclusively; frontend agent owns src/ exclusively (all React/types/services/styles). Root owns tooling/config/ops/docs/tests integration. Coordinate contract changes via messages before editing outside ownership.
